# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/2.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

## [2.0.1] - 2026-10-26

### Fixed

* A tool result holding bytes that are not UTF-8, such as `cut -c` output cut inside Arabic text, no longer breaks the conversation. Every later request failed with `jsontext: invalid UTF-8 within "/messages/…"` and the conversation stopped being saved. `run_command` now drops a broken character from a short output, as it already did for a long one, and any other tool's invalid bytes become U+FFFD. The last lines of a background job, given to the model when it ends, no longer start with a broken character when a long line is cut.

## [2.0.0] - 2026-10-25

This is a major rewrite and breaks compatibility with the 1.0.x releases. Saved conversations, some config files, command lines and scripts that worked with an older version need changes:

### Breaking changes

* Conversations are saved one file per conversation in `~/.hmj/projects/<slug>/conversations/`, beside `state.json`. An existing `sessions.json` is not read, so conversations saved by an older version are not carried over; the file can be deleted. `HMJ_SESSIONS` now names the session directory, not a file.
* Each command-line flag has one spelling (`--help`/`-h`, `--version`/`-v`, `--health`, `--accessible`/`-a`, `--high-contrast`, `--no-color`, `--strict`). `help`, `version`, `health`, `shortcuts`, `/shortcuts`, `--shortcuts` and `--accessibility` are gone, and any other argument exits with code 2.
* A config key hmj does not know is an error. The `contextWindow` model setting is removed, so a config that still sets it must drop it.
* Claude models before the Claude 5 family are no longer supported.
* `run_command` returns stdout and stderr as one stream, without the `[stdout]` and `[stderr]` sections.

### Changes

* Two or more hmj can run in the same project, for example on different parts of it, without losing each other's conversations. Each conversation is saved in a file of its own, `~/.hmj/projects/<slug>/conversations/<id>.json`, beside `state.json` with the last active conversation and the default model; `HMJ_SESSIONS` now names that directory. An hmj locks the conversation it has open and writes only that one, so a second hmj starts its own conversation, its `/resume` lists the first one's marked `[open in another hmj]`, and opening, renaming or deleting it is refused with `conversation 1 is open in another hmj (pid 4242)`. `/resume` shows conversations another hmj created, renamed or deleted, and opening one reads its latest turns. New conversations never share an ID, and a deleted conversation's ID is not given out again (`state.json` keeps the highest). Before, both rewrote one `sessions.json` with what each held in memory, so the last to save dropped the other's new conversations and turns. Saving also writes only the active conversation instead of all of them. **Breaking:** an existing `sessions.json` is not read; its conversations are not carried over, and the file can be deleted. Their scratch directories and compacted histories are removed as orphans at the next start, once unchanged for an hour.
* The system prompt tells the model that what tools return (web pages, search results, file contents, command output) is information, not instructions: it follows the user and the project guidelines, and steps in a file or page when the user asks it to, and tells the user instead of acting when such content asks for something the user did not, such as running a command or sending data somewhere. Nothing it can do is taken away. Conversations already started keep their prompt.
* A conversation whose ID is empty, `.`, `..` or holds a slash is not loaded, nor is a conversation file whose name starts with a dot. The ID names the conversation's scratch directory, which deleting the conversation removes, so a damaged or hand-edited session could have pointed that removal outside the scratch root.
* Copies from `Ctrl+Y` (`/history`) leave out escape sequences and control characters other than tabs and newlines. A response holding `ESC [201~`, which ends a bracketed paste, followed by a command would have run that command when pasted into a shell. The copy is otherwise the raw Markdown, right-to-left text included.
* Bidirectional embedding, override and isolate controls (U+202A–U+202E, U+2066–U+2069) in file contents, diffs, command output and the model's text are shown as `<U+202E>` and the like. They reordered the text around them, so a diff could show code that reads differently from what the file holds ("Trojan Source"). Arabic and Hebrew text, and the plain left-to-right and right-to-left marks, are unchanged.
* DCS, SOS, PM and APC escape strings (`ESC P`, `ESC X`, `ESC ^`, `ESC _`) in text hmj shows are dropped up to their terminator, as OSC strings already were; only their first two bytes were removed, so the payload showed up as text.
* A provider's error can no longer drive the terminal. A failed request, a retry notice, a compaction that failed, `/history`'s note on unreadable compacted turns and the `/health` details cell printed the provider's error body and headers as they came, so a proxy or an endpoint answering in plain text could send escape sequences (an OSC 52 clipboard write, a title change, a screen clear) to the terminal. They are dropped from what is shown; the diagnostic log (`HMJ_LOG`) keeps the body as it arrived. `/health` also puts a multi-line error on one line.
* Any non-empty `NO_COLOR` turns colour off, as no-color.org asks; `NO_COLOR=0`, `false`, `no` and `off` left it on. `FORCE_COLOR` (any value) and `CLICOLOR_FORCE` (other than `0`) turn colour on for piped output and `TERM=dumb`; `NO_COLOR` wins over both.
* In accessibility mode the `/jobs` menu's title no longer offers Enter and Esc, which do nothing in its numbered list.
* hmj no longer wakes up ten times a second while it waits at the prompt; it used to check for a finished background job that way, and now sleeps until a key or the job's end arrives.
* fetch_url keeps at most 16MB of fetched pages in memory for its 15-minute cache, where it kept 64MB; a page over 16MB is not cached.
* Building a request for a long conversation takes about a third less time and memory (for a conversation of 400K tokens with 20 pictures, 15 ms and 35MB instead of 26 ms and 60MB), and rendering a long answer allocates 30% less.
* `hmj --health` no longer reports a model healthy when its answer ends before the first byte of the body, and an error answer whose body is cut off says so after what could be read. Protocol detection treats a probe answer that cannot be read as no answer, instead of classifying the part that arrived.
* In accessibility mode, a delete confirmation that input ends before (`y` with no Enter at end of input) cancels the delete; it deleted.
* A turn, compaction or title request halted while hmj is still detecting the provider's protocol stops there, without sending its request.
* A failure to switch the terminal's mode, which can leave keys echoed or waiting for Enter, is reported once on stderr instead of silently. Files hmj cleans up in the background (old backups, idle scratch directories, orphaned history, a deleted conversation's files) that cannot be removed are noted in the diagnostic log (`HMJ_LOG`), and a scratch directory whose age cannot be read is kept.
* Each command-line flag has one spelling: `--help`/`-h`, `--version`/`-v`, `--health`, `--accessible`/`-a`, `--high-contrast`, `--no-color` and `--strict`. `help`, `version`, `health`, `shortcuts`, `/shortcuts`, `--shortcuts` and `--accessibility` are gone, and any other argument stops hmj with `unknown argument "..."` and exit code 2, where it was silently ignored, so `hmj --acessible` started without accessibility mode.
* A config file key hmj does not know is an error naming the key and the file, such as a misspelt `baseURL` or the removed `contextWindow`. Such keys were ignored, so a typo silently left a setting at its default.
* A turn whose first output is a tool call has one blank line below the prompt, not two: the turn printed a blank line as it started, and the tool call another of its own. A turn starting with text or reasoning is unchanged.
* On a terminal, the model's text sits behind a 2-column margin and is word-wrapped to the window, so a wrapped line keeps the margin instead of returning to column 0. A list item's wrapped lines hang under its text, a quote's repeat its bar, and bold or code broken across lines keeps its style. Code fences and tables get the margin but are not wrapped. Tool calls, the footer and the prompt stay at column 0. Accessibility mode and output that is not a terminal keep lines as the model wrote them.
* The model's Markdown is rendered: `**bold**`, `*italic*` and `` `code` `` lose their markers and take their style, `#` headings show in the title style, `-`/`*`/`+` bullets as `•`, `>` quotes behind a faint bar and `---` as a rule, while code fences and the lines in them are shown as written. Answers printed `**Findings**` with its asterisks. Each line is rendered once complete, as tables already were, so streaming is unchanged; the same applies to a resumed conversation and to `/history`'s view, where tool calls and results stay as written. A marker is removed only when its pair closes on the same line, so `2*3*4`, `snake_case` and `__init__` are untouched. Copies from `Ctrl+Y` are the raw Markdown, and with colour off (`--no-color`, `NO_COLOR`) answers print as written. Accessibility mode uses `-` bullets and a `|` bar.
* A finished turn is set off from the next prompt by a blank line and a dim rule, at most 80 columns wide (`----` in accessibility mode). The answer's last line, the footer, the model line and the next prompt followed one another with no space, so in a long session it was hard to see where one turn ended and the next began. The prompt after the banner or a command such as `/history` gets no rule.
* A conversation's `updatedAt` in `sessions.json` is set when each turn ends, completed, halted or failed, and when the conversation is compacted. It changed only when the conversation was named, so a conversation used for hours kept the time of its first exchange.
* `/history` (`Ctrl+Y`) lists the turns a compaction replaced, marked `(compacted)`, before the turns since, and can view and copy them. A compaction dropped them from the saved conversation, so after one the turn browser started at the first turn after it. The replaced messages' text, tool calls and results, without reasoning blocks or pictures, go to `~/.hmj/projects/<slug>/history/<id>.jsonl` when the compaction is applied; the file goes with its conversation. When it cannot be written, the conversation is compacted all the same and a warning says the earlier turns were not kept. Conversations compacted before this change keep only the turns since.
* Long commands can run in the background while you keep talking to the model. `run_command` takes `background: true`: the call returns at once with a job number, and the command runs on for up to 4 hours (`timeout_seconds` lowers that), its output in `$HMJ_SCRATCH/jobs/`. `Ctrl+B` under a running command moves it to the background the same way: the call returns the output so far, and the turn ends there, skipping the step's other calls as `Esc` does, so the prompt comes back at once instead of when the model chooses to stop. When a job ends, the model is told its exit code, time and last lines: in its next tool result while it is working, or in a turn that starts by itself when the prompt is empty; with text typed, nothing starts and the notice goes with your message. Each conversation numbers its own jobs, from 1 and on from its earlier logs after a restart; before, numbers ran across the whole hmj session, so a conversation's first job could be job 2. A new `check_command` tool reports on one of its conversation's jobs or stops it, `/jobs` lists every conversation's jobs, naming the conversation of the others, and stops one, the prompt line counts running jobs, and quitting hmj stops them. The tool description and the system prompt ask the model to start commands over about two minutes in the background and end its turn. A session spent 105 of 140 minutes in four 12–14 minute device test runs, and the user had to halt one to say something.
* A `run_command` result notes a `sed -i` or `perl -i` (`-i.bak`, `-pi`, `--in-place`): `[note: sed -i changes files with no diff shown and no backup kept; for project files use edit_file]`. Even with the system prompt asking for the file tools, a session edited a source file and `strings.xml` with `sed -i`; earlier sessions had done so 17 times. Commands that name the scratch directory get no note.
* An `edit_file` call with several `edits`, one of which has the same `old_string` and `new_string`, makes the others and notes the one that changed nothing: `[note: edit 1 of 3 changed nothing, as old_string and new_string are identical]`. The whole call was refused, where a single such edit was already answered `no changes`; a session lost two real edits to one unchanged anchor. The unchanged edit must still match the file, and a call of only such edits changes nothing.
* The turn footer ends with the local time the turn was done, after its duration: `2h20m total, done at 18:01`. A turn of two hours and more, left running, otherwise gave no sign on return of when it had finished. Durations of a minute or more, in the footer, tool results and retry notices, read as the status line counts them, `14m26s` or `2h20m`, where they were seconds: `866.0s`, `8400.0s total`.
* A diff shows only the lines that changed, also when one `edit_file` call changes places far apart in a long file. A changed region of more than about 300 by 300 lines was shown as all removed and then all added: a session's 12-edit call on a 700-line file, a change of 15 lines removed and 24 added, printed as `+634 / -625 lines`, 117 rows of unchanged imports marked removed, and `… 1145 more changed lines not shown`. Such a region is now split at lines that occur once in each version, and each part is diffed on its own; only a region with no such line left is shown whole.
* The system prompt asks the model to work on files with the file tools, `grep`, `list_files`, `read_file`, `edit_file` and `write_file`, and to keep `run_command` for builds, tests, git and device commands. A session searched 15 times with `grep`, `sed -n`, `cat` and `find` through `run_command` and never called `grep`, and made 4 edits with `python3` heredocs, which show no diff and leave no backup.
* A `grep` result starts with the search its arguments asked for, such as `[searched for "x" in . (no path given)]`. A session sent `grep` with pattern `x` and no path four times, among correct calls; each time the model blamed a missing path and never saw that the pattern was not the one it meant. The transcript's one-line summary is unchanged.
* `fetch_url` reads up to 16MB of a response, up from 4MB, and says so when a response was cut. An Android reference page (`developer.android.com/reference/kotlin/.../LazyListState`) is 4.4MB, mostly inline navigation, and its `<main>` starts past the first 4MB: the page came back as 370 characters of its language menu, with no sign that anything was missing, and the model spent six more calls looking for the documentation elsewhere.
* The system prompt asks the model to fix a defect it finds in its own output, such as a screenshot, log or generated file, and check again before it concludes, and to report as open only what it cannot fix, with the reason. A session noticed that a test's screenshot was blank because it was taken before the screen loaded, and listed it under problems instead of adding the wait. New conversations get the prompt; ones already started keep theirs.
* `run_command` runs commands under `sh -o pipefail` when `sh` accepts it, so a pipeline fails when any command in it fails. A session ran `./gradlew :sms:lintDebug -q 2>&1 | tail -15; echo exit=$?` and took `exit=0`, the status of `tail`, as proof that lint passed. A pipeline whose reader stopped early, such as `yes | head -1`, now ends with `[Exit code 141: ...]` and a note that SIGPIPE is usually not an error. An exit code 1 from a command that runs `grep`, `rg`, `diff` or `cmp` says that they also exit 1 when they match nothing or find a difference: a session checked for failed tests with `grep -l "<failure" *.xml | head`, and finding none came back as `[Exit code 1]`. The note blames pipefail only when that command's output goes into a pipe; at the end of a command, such as `cat log; grep BUILD log`, the 1 is its own status. The tool description says so too: a session filtered a clean lint with `| grep -v "^w:" | tail -15; echo exit $?`, read `exit 1` and ran lint again.
* A tool call that repeats the previous one, with the same arguments and the same result, gets a note in its result saying so. A model that believes it changed something may otherwise send the same call again and again: a session sent one `grep` 8 times, reading each identical result as a new failure.
* `[halted by user (Esc)]` prints at the end of the halted turn, before its footer, instead of the moment the key is pressed, where it landed above the cancelled command's `[command cancelled by user]` and its time. Until the work has stopped, the status line says `halting…`.
* A `run_command` call of more than 4 lines, such as a script in a heredoc, shows its first 3 lines and `… N more lines` instead of the whole script. `Ctrl+Y` still shows it whole.
* The transcript has exactly one blank line between blocks: the model's text, the `Thought for` line and each tool call. Text that ended in a line break was followed by two blank lines before the next tool call, and text or a `Thought for` line after a tool's result had none, so the line read as part of the call above it.
* Claude's tool calls arrive with the arguments it meant, and it can use the tools' optional parameters again. Tools were sent with `strict`, under which Claude must write a tool's arguments in the order its schema lists them, skipping optional ones but never moving them, and Claude does not keep to one order. With the schemas sorted, `edit_file` calls came with neither `old_string` nor `new_string` and failed with `old_string cannot be empty`, and `read_file` never got `offset` or `limit`; with `grep` declaring `pattern` first, a model that meant to write `output_mode` and `path` first and its long pattern last sent `{"pattern": "x", "output_mode": …}`, its path and real pattern lost, in 23 of 32 replays of one session (0 of 27 without `strict`). No tool is strict now; each checks its own arguments, as for every other provider. Each tool still declares its properties' order (`path`, `old_string`, `new_string`, …), which every provider is sent and the cache sees unchanged from run to run.
* `install.sh` installs hmj from a GitHub release, or updates it when run again: `curl -fsSL https://raw.githubusercontent.com/himanshu-mahendra-jain/hmj-agent/main/install.sh | sh`. It picks the Linux amd64 or arm64 tarball of the latest published release, or of `HMJ_VERSION`, checks it against the release's `SHA256SUMS.txt`, and renames it over `~/.local/bin/hmj` (or `HMJ_INSTALL_DIR`), so a running hmj is not disturbed. It does nothing when that version is already installed, and says so when the directory is not on `PATH`. Draft releases are not seen until they are published.
* The line before each prompt and each `/models` entry show the reasoning effort the model's requests carry: `[model: anthropic/claude-opus-5-5 · effort: high]`. It reads `default` when none is set, `high (from xhigh)` where Gemini narrows `xhigh` or `max`, and `default (high not sent: …)` for Chat Completions, which has no effort field, or with `"thinking": "off"` outside Anthropic.
* Each saved conversation has a scratch directory, `~/.hmj/projects/<slug>/scratch/<id>/`, created when a turn starts. Its system prompt names it, asking for temporary files there rather than in `/tmp` or the project, and `run_command` passes it as `$HMJ_SCRATCH`; the prompt asks the model to give the user a scratch file's full path, since the variable is not set in the user's shell (a session pointed the user to `$HMJ_SCRATCH/summary.tsv.bak`). In earlier sessions the model wrote logs and file copies to `/tmp` under names such as `/tmp/jvm_baseline.log`, which other sessions reuse, and left some behind. A directory goes with its conversation, and on start any unchanged for 7 days, or for an hour when its conversation is gone, is removed.
* While the model writes a tool call, the status line says so, such as `writing write_file (12s) · 14 KB`, with the size of its arguments growing as they arrive. After the model's text, the screen used to stand still for as long as a large `write_file` took to write. Anthropic, OpenAI Responses, Chat Completions and Gemini all report it. Claude holds a tool's input back until each value is complete, so `write_file` and `edit_file` are sent with `eager_input_streaming`, which streams their input as it is written.
* The model's reasoning no longer prints into the transcript. While it thinks, the status line shows the latest sentence of its reasoning as the provider sends it, and once it is done one line stays: `▸ Thought for 8s`, timed from the request or from the answer text before it, since Claude may send its summary of the reasoning only at the end. Accessibility mode prints the same line (`> Thought for 8s`) in place of the reasoning and its `[END THOUGHTS]` label.
* The transcript sums up what the model reads instead of printing it. `read_file`, `list_files`, `grep`, `fetch_url` and `web_search` print one line once they finish, with the call, what it found and the time it took: `read_file: src/app.go · 120 lines · 3ms`, `grep: TODO (glob: *.go) · 43 matches in 9 files`, `fetch_url: … · 12 KB, 340 lines`; while they run, the status line names the call. `web_search` adds a line per result with its title and site. `run_command` shows its last 10 output lines, where builds and test runners print failures and totals, under `… N lines hidden`. Diffs and errors still print in full, resumed conversations use the same lines, and the turn browser (`Ctrl+Y`) still shows every result whole. `list_files` calls show their `pattern`.
* Anthropic requests default to `max_tokens` 64000, up from 32000, as Anthropic recommends for agentic work: a response cut off at the limit fails the step, and the higher limit costs nothing until it is used. A model with a smaller output limit needs `maxOutputTokens`.
* `read_file` of a PNG, JPEG, GIF or WebP file returns the picture, so the model can look at screenshots from device tests or `adb exec-out screencap -p`, mockups and diagrams. A picture within 2000px a side and 3.75MB is sent unchanged; a larger PNG, JPEG or GIF is scaled to fit in pure Go, as PNG, or JPEG for a photo or a PNG still too large. A WebP that is too large, a corrupt picture, or a session without an image store gets the one-line description and the reason. The transcript shows `image` with the picture's size and how it was sent.
* A tool result can carry pictures after its text. They are stored once in `~/.hmj/images/` and the conversation refers to them, so `sessions.json` holds no image data. Anthropic gets them as `image` blocks in the `tool_result`, OpenAI Responses as `input_image` parts of the `function_call_output`, and Gemini as `image` parts of the `function_result`; Chat Completions, whose tool results are text only, and a picture pruned from the store get a note naming the picture instead.
* `read_file` describes a binary file in one line, such as `PNG image, 1080×2400, 72 KB` or `Android APK (ZIP archive), 30.0 MB`, with a command to look inside (`unzip -l`, `readelf -h`, `sqlite3 .tables`, `javap`, `pdftotext`, `iconv` for UTF-16, `xxd`), instead of returning its bytes; a screenshot cost about 30K tokens of noise. Files are judged by their first 8KB, so a binary over the 10MB cap is described too, and UTF-8 or Latin-1 text still reads as text.
* `web_search` results name the source that answered and today's date, against which dates such as `2 days ago` can be read, and list the sources that failed first. A search repeated within 15 minutes, with the same filters and limit, is answered from a cache and says so; failures and empty answers are not kept.
* `web_search` takes `allowed_domains` and `blocked_domains`, which reach the engines as `site:` and `-site:` operators and are checked again on the results, subdomains included, and `recency` (`day`, `week`, `month` or `year`), which each engine gets in its own form; a source that cannot filter by that recency is skipped. The transcript shows the filters after the query.
* `web_search` falls back to Brave's and then Bing's result pages when DuckDuckGo fails or blocks the address, which it does with a `202` status (now reported as a bot challenge). Wikipedia is searched by article text rather than by title prefix, which matched little but the query's first words. Results show the page's date when Brave, Bing or Wikipedia give one, and snippets are kept to 400 bytes.
* `web_search` pairs each DuckDuckGo snippet with its own result: a result without a snippet shifted every later snippet onto the wrong result. Ads and repeated URLs are left out, and links with `&amp;` in them are decoded. Instant-answer topics show their name as the title and the rest as the snippet, where the whole text was both, and grouped topics are included.
* `read_file` numbers lines by default (`  12 | text`), which the model needs to point at code and to pick an `offset`; `"numbered": false` returns the exact text. Its description and `edit_file`'s error say the prefixes are not part of the file, when an `old_string` carries them.
* `read_file` of a directory returns its listing, as `list_files` with `max_depth` 3, instead of an error.
* `list_files` takes a `pattern`, a glob such as `*.go`, `*.{ts,tsx}` or `src/**/*Test.kt`, and then lists only the files it matches, at any depth unless `max_depth` is given.
* A new `grep` tool searches file contents with a Go regular expression, or plain text with `literal`, without leaving hmj. It walks a directory as `list_files` does, skipping `.git`, binary files and what `.gitignore` ignores, or searches one file. It returns the matching files (the default), the matching lines as `path:line:text` with optional `context` lines, or a count per file, can filter by a `glob` such as `*.{ts,tsx}` or `src/**/*Test.kt`, and stops at `head_limit` (default 250, at most 2000) and 64KB with a note that more matches exist.
* `edit_file` takes several replacements in one call as `edits`, each with its own `old_string`, `new_string` and `replace_all`. They apply in order, each to the text the earlier ones left; if one fails, the error names it and the file is unchanged. One backup is kept and one diff of the whole call is shown. The diff shown for any `edit_file` call is now worked out as the tool applies it, so `replace_all` and `ignore_whitespace` edits show every change.
* The model's `[text](url)` links are rendered. A link to a web page shows its text, underlined, which the terminal opens when clicked (OSC 8). A link to a file shows its text and then its path, relative to the project when inside it: `conv_39.png (screenshots/sms/conv_39.png)`. A terminal often cannot open a `file://` link (ChromeOS's opens it outside the Linux container), so the path is what finds the file. Wrapping no longer cuts a linked word, so a long path stays whole; a session's `[conv_39.png](file:///home/…/conv_39.png)` printed raw, its path split across two lines. In tables the label is a link and the path follows it. Other links, such as `mailto:`, and every link with colour off print as written; `Ctrl+Y` copies stay raw Markdown.
* A signal that arrives while hmj quits, such as the `SIGHUP` of a terminal tab closing just after `Ctrl+D`, waits for the quit to finish instead of saving the conversation a second time. The quit ended the process in the middle of that second save, leaving an empty `.<id>.json.tmp…` file beside the conversation. Such files, which a killed hmj can still leave, are removed at the next start once a minute old.
* The system prompt has the model answer a question, or a request for its opinion or suggestions, and propose changes rather than make them, changing only what the user asked for, and answer questions before starting long work. A model asked whether it suggested improvements to filter rules rewrote them instead, and answered the user's other questions an hour later.
* `read_file` on a file named as a picture that does not start like one, such as a screenshot `adb shell screencap -p` began with a warning, says so and quotes how the file starts. When the picture follows in its first 8KB, it gives the byte where it starts and a `tail -c` command that cuts what comes before. Descriptions of binary files say `read_file` shows text and pictures, not only text.
* Where `sh` is not bash, as on Debian and Ubuntu, `run_command`'s description says which shell it is and that it lacks bash-only syntax such as `$'\t'`, `[[ ]]`, arrays and `<(…)`, pointing to `bash -c`. A model wrote `sort -t$'\t'`, which dash passed on as `$\t`.
* `check_command` asked for a job started before hmj restarted gives that job's log, instead of saying the conversation has no background jobs.
* A command that exits 0 while a process it left running still holds its output, such as the `sleep` of a sampler subshell it killed or a server it started, is reported as exit 0 with that reason. It was reported as `exec: WaitDelay expired before I/O complete`, which hid the exit status: a 20-minute test job ended that way.
* A reopened conversation tells the model, with the next message, of background jobs whose end it never heard of because hmj stopped or was killed while they ran: when the job's log was last written, its last lines and the log's path. Reopening such a conversation says so under its history, so the user knows before typing. Before, the model went on as if the job were still running and only learned otherwise if it asked `check_command`.
* A turn saves the conversation as it goes, once the prompt is added and after each step's tool results. An hmj killed outright mid-turn, as by the out-of-memory killer, kept nothing of the turn, since it saved only when the turn ended or on a signal it could catch; it now loses at most the step under way.
* Chat Completions sends a model's `maxOutputTokens` to OpenAI's own API and Azure OpenAI as `max_completion_tokens`, which OpenAI asks for in place of the deprecated `max_tokens` and which its reasoning models require. Other servers still get `max_tokens`.
* A model's `effort` takes all of OpenAI's levels: `none` and `minimal` join `low`, `medium`, `high`, `xhigh` and `max`. Anthropic gets `none` and `minimal` as `low` and Gemini as `minimal`, shown as `low (from minimal)`. Chat Completions now sends the effort as `reasoning_effort` unless thinking is off; it was never sent.
* An OpenAI Responses reply whose message items carry a `phase` (`commentary` or `final_answer`) keeps each item with its phase, and later requests send them back that way. OpenAI asks for this from `gpt-5.3-codex` on, saying that dropping it can degrade performance; the phases were dropped and the text sent back as one unlabelled message. Replies without phases are sent back as before.
* OpenAI Responses requests always send `store: false`. With thinking off it was left out, and the API then defaults to storing each response for 30 days, which hmj never reads back since it sends the whole conversation every turn.
* An OpenAI Responses stream that reports an `error` event or ends with `response.failed` stops the step with the API's code and message, such as `openai error (invalid_prompt): …`, and is retried for `server_error` and `rate_limit_exceeded`. Both were ignored, so a failed response came back as an empty reply. A Chat Completions chunk holding `error`, which vLLM and OpenRouter send mid-stream, is reported the same way.
* OpenAI Responses requests give each function tool its `name`, `description` and `parameters` beside `type`, with `strict: false`, as the API requires. They went nested under `function`, the Chat Completions shape, which OpenAI refuses with `Missing required parameter: 'tools[0].name'`, so every turn on a Responses provider failed. `strict: false` keeps optional tool arguments optional; left out, the API makes a schema strict where it can, requiring every property.
* A conversation left without a prompt sent in it, by `/new`, `/resume` or deleting the active one, is removed instead of kept: `/resume` had listed an empty `conversation-18` from a `/new` that was never used. One that was renamed is kept, and quitting keeps the open one, so the next start reopens it rather than an older conversation.
* A resumed conversation shows each `edit_file` call's old and new text as written, not a diff against the file as it is now. When the file still held the edit's old text, as an insertion after an unchanged line does, the edit was applied a second time for display, so a session's import or string resources showed up twice, with wrong line numbers, though the file had them once. A call with one edit in `edits` says `(1 edit)`, not `(1 edits)`.
* A resumed conversation prints each step in the order the turn did: the model's text, then each tool call followed by its own result. It printed the calls first, then the text, then the results, so with several calls in one step every output landed under the last call: an `edit_file` result and the output of `adb devices` both showed under the command after them.
* A resumed conversation shows a turn started by finished background jobs as the turn did: each notice's first line, after the prompt typed with it if there was one. It showed `> you: [background job 4 finished: …]` followed by the job's whole output, as if the user had typed it. Notices of jobs that finished while a tool ran, which end that tool's result, show after the result the same way; they were shown whole inside it, where a job's 20 output lines took the place of the command's own last lines. The banner and `/resume` count only the prompts the user typed: a session with 3 prompts and 3 finished jobs said `(6 messages)`.
* `run_command` accepts `timeout_seconds` up to 1800 (30 minutes), up from 300, so a full build or device test suite runs as one call instead of in the background with polling. The status line shows its output meanwhile, and `Esc` halts it.
* `run_command` returns stdout and stderr as one stream, in the order the command wrote them, instead of separate `[stdout]` and `[stderr]` sections. An output over 64KB keeps its first 16KB and its last 48KB, cut on whole lines, where it kept only the first 64KB; failures at the end of a build or test run now reach the model. The whole output is saved to `~/.hmj/commands/` (at most 64MB per file, 100 files and 256MB in all) and the result names the file.
* A status line now runs under a tool call, as it did only while waiting for the model. It names the tool and counts the time (`2m14s`), and for `run_command` shows the latest output line, including one still being written, such as a test runner's dots. While the model works on a later step it shows the step, the prompt and output tokens and tokens/s. The line is cut to the terminal width. Accessibility mode keeps its `[running]` lines.
* A turn whose request fails still prints its footer, counting the steps that completed before the failure.
* A model may set `"speed": "fast"` to request Anthropic fast mode. The turn footer says `fast mode` when the API reports that the turn ran at fast speed.
* The turn footer counts prompt-cache reads for Anthropic and Gemini models; it showed them only for the OpenAI protocols.
* Conversations are compacted only once the prompt passes 400K tokens, after a turn ends and never inside one, for every protocol. Claude conversations use Anthropic's on-demand compaction, OpenAI Responses conversations use `POST /responses/compact`, and Gemini and Chat Completions conversations, or a provider that rejects the compact endpoint, get a summary the model writes. The compaction runs while the next prompt is typed; a prompt sent before it ends waits for it, and `Esc` or `Ctrl+C` stops it.
* Tool output is no longer pruned between turns, older turns are no longer summarized after six turns, and the `contextWindow` model setting is removed. The transcript stays as sent until it is compacted, so Claude thinking blocks stay valid. Session files written by earlier versions are no longer repaired on load: a pruned conversation keeps thinking blocks Claude may reject with `Invalid signature in thinking block`, and tool calls left without a result stay open, which providers reject. Start a new conversation for either.
* Credentials are no longer masked as `[REDACTED]` in the saved session file, the audit and diagnostic logs, or provider errors, since hmj is meant for a dedicated VM. A resumed conversation is now exactly the one the model produced: masking changed the text of signed Claude thinking blocks and compactions that quoted a credential, and the API then rejected every later request of that conversation.
* `run_command` passes hmj's whole environment to commands, including variables ending in `_API_KEY`, `_TOKEN`, `_SECRET` or `_PASSWORD` and those an `"apiKey": "$VAR"` names, and hmj no longer marks itself non-dumpable. Tools such as `gh` can use a token from the environment.
* A compacted conversation keeps its title.
* Anthropic requests send `anthropic-version: 2026-10-21`.
* The conversation title request to a Claude model asks for low effort and allows 256 output tokens, as for the other reasoning protocols, instead of turning thinking off with a 40-token cap: Claude 5 models think regardless, and the thinking could use up the cap before any title was written.
* The starter config written on the first run is updated, with API keys read from environment variables.
* The turn footer's output speed and time to first token now count a step that only calls tools from when its tool call starts, on the Anthropic and Chat Completions protocols. Before, the whole step counted as output time, so a tool-using turn showed a speed far too low.
* In a multi-step turn the footer shows the cached tokens of the latest step, matching the input it shows, instead of adding up every step's cached tokens.
* Each model step in the diagnostic log (`HMJ_LOG`) records its time to first output (`ttft`) and cached tokens.
* Model requests no longer ask for gzip-compressed responses: an event stream gains little from compression, and a compressing proxy may hold the stream back before passing it on.
* The diagnostic log (`HMJ_LOG`) records each model response: how long its headers took, the HTTP version, any content encoding, the provider's request ID, and for Anthropic the organization and workspace the API key ran in.
* Anthropic, Gemini and OpenAI requests list map keys, including each tool's schema keys, in sorted order. They came out in a random order on each run, so the request bytes the API caches changed from run to run.
* A Claude response whose stream closes before its stop reason is no longer taken as complete, so a tool call with cut-off arguments, such as a half-written `write_file`, never runs. It is retried when no output has been shown, and reported as an error otherwise.
* Rate-limit (`rate_limit_error`) and timeout (`timeout_error`) errors that the Anthropic API reports inside a stream are retried before output starts, as overload and server errors were and as their HTTP 429 and 504 forms are.
* Claude models before the Claude 5 family, such as Opus 4.6 and 4.8, are no longer supported.
* `fetch_url` caps its output at 64KB as well as by lines, so a response that is one long line, such as minified code or a base64 file, no longer reaches the model whole. A page cut by either limit is saved whole to `~/.hmj/fetch/` (the newest 100, up to 256MB), and the result names the file for `read_file` or `grep`.
* `fetch_url` asks for Markdown first (`Accept: text/markdown`), which sites with Cloudflare's Markdown for Agents and many docs platforms serve, and no longer converts a Markdown, plain text or JSON response as HTML because it quotes `<html`. It fetches a GitHub `blob` page as the raw file, decodes base64 file sources such as googlesource `?format=TEXT`, and indents JSON. Its description points to `llms.txt`, `llms-full.txt` and `.md` page variants.
* `fetch_url` converts only an HTML page's `<main>` element, or its `<article>` elements, after the page title; a page with neither loses its `<nav>`, `<footer>` and `<aside>`. On MDN a page went from 43KB to 5KB of text with the article intact.
* `fetch_url` takes `timeout_seconds` (default 20, up to 120) for the whole response, and a timed-out fetch says how to wait longer. When redirects end on another host, the result names the final URL.
* `fetch_url` answers a URL fetched in the last 15 minutes from that copy, saying how old it is. Local and private hosts and error responses are always fetched again.
* A tool result is capped at 320KB before it is sent. A request the provider rejects as over the model's context limit is sent again without the largest tool result of the current step, replaced by a note; the note stays if the request still fails, so the saved conversation can be sent again instead of failing the same way.
* A model set to `"thinking": "off"` gets the same 256-token limit for its conversation title request as other models, instead of 40 tokens. Many such models reason anyway, Claude among them, and the reasoning used up the 40 tokens, so the conversation kept its automatic name. An Anthropic model with `"off"` and an `effort` set asks for low effort for the title.
* HTTP 409 (`conflict_error`) is retried, as the official Anthropic SDKs do.
* An Anthropic error response is shown as its type and message, such as `HTTP 402: billing_error: Your credit balance is too low.`, instead of its raw JSON. HTTP error responses and errors the API reports inside a stream end with the request ID (`request_id req_…`) that Anthropic support asks for; the diagnostic log (`HMJ_LOG`) has it for every response.
* A Gemini or OpenAI Responses error response is shown as its code and message, such as `HTTP 400: invalid_request: Request contains an invalid argument.`, instead of its raw JSON, also when Gemini sends it framed as a stream error event.
* Error hints: a 403 points at the account's and workspace's access to the model as well as the API key, and 402 (billing) and 413 (request too large) get hints of their own.
